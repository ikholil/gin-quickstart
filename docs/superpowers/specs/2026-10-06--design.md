# Ecommerce API MVP Design

## Goal

Turn the Gin `/ping` starter into a maintainable ecommerce API that supports customer accounts, product discovery, carts, order placement, and the basic admin operations needed to run the catalog and review orders.

The first milestone is a single deployable API. It does not process payments or integrate with shipping carriers.

## Decisions

- Use a layered Gin monolith with HTTP handlers, services for business rules, and SQLite repositories.
- Use a pure-Go SQLite driver and versioned schema migrations so local setup does not require a separate database server or CGO.
- Prefix application routes with `/api/v1`.
- Store all prices and totals as integer USD cents.
- Authenticate customers and admins with bcrypt-hashed passwords and JWT bearer tokens.
- Require explicit environment configuration for JWT signing and provision the initial admin only from an explicitly supplied email/password pair.
- Create orders as `pending`. Checkout atomically creates the order, decrements inventory, and empties the cart.
- The order API state is only `pending` or `cancelled`; there is no persisted or public payment status/field. Any notion of “unpaid” is implicit business context because payment processing is out of scope.
- Require a shipping address at checkout and snapshot it on the order. Shipping calculations, labels, and carrier integrations are not part of this milestone.
- Allow admins to cancel only pending orders. Cancellation atomically restores the ordered quantities; it cannot be applied twice.
- Archive rather than delete products referenced by order history.

## Scope

### Included

- Customer registration and login.
- Public category and active product reads, with product search/filtering and bounded pagination.
- Customer-owned persistent cart operations.
- Checkout and customer-owned order history/detail.
- Admin category and product create/update/archive operations.
- Admin paginated order listing/detail and pending-order cancellation.
- Health/readiness endpoints, JSON validation/errors, configuration, migrations, and automated tests.

### Excluded

- Payment processing, refunds, and payment-provider webhooks.
- Shipping rates, carrier integrations, and fulfillment automation.
- Coupons, taxes, multiple currencies, reviews, wish lists, and guest checkout.
- Multi-tenant stores or separate microservices.

## Architecture and data

The request path is:

1. Gin router applies request logging, panic recovery, and route-specific authentication/role middleware.
2. Handlers decode and validate transport input, call a service, and encode the API response.
3. Services enforce ownership and ecommerce invariants.
4. Repositories execute parameterized SQLite queries; checkout and cancellation use database transactions.

Keep transport, service, and persistence responsibilities in separate packages under `internal/`. Keep the router and process startup in `main.go` or a small application package. Store ordered SQL migrations in a dedicated migrations directory.

Core records:

- **User:** unique normalized email, password hash, customer/admin role, timestamps.
- **Category:** name, active/archive state, timestamps.
- **Product:** category, name, description, price in USD cents, available stock, active/archive state, timestamps.
- **Cart and cart item:** customer owner, product, positive quantity; one persistent cart per customer and one line per product.
- **Order:** customer, pending/cancelled state, USD-cent total, immutable shipping-address snapshot, timestamps.
- **Order item:** order, product reference when retained, immutable product-name and unit-price snapshots, quantity, and line total.

Foreign keys must be enabled. Email and cart-line uniqueness are enforced by the database. User-supplied prices, totals, roles, and order state are never trusted. Product archival preserves order snapshots and prevents new cart/checkout use.

## API surface

All business routes are under `/api/v1`. The operational liveness/readiness probes (`/healthz` and `/readyz`) are intentionally unversioned and are the only exceptions.

| Method | Path | Access | Behavior |
|---|---|---|---|
| `POST` | `/auth/register` | Public | Create a customer account |
| `POST` | `/auth/login` | Public | Verify credentials and return a JWT |
| `GET` | `/categories` | Public | List active categories |
| `GET` | `/categories/:id` | Public | Read an active category |
| `GET` | `/products` | Public | List active products; supports text/category filters and bounded pagination |
| `GET` | `/products/:id` | Public | Read an active product |
| `GET` | `/cart` | Customer | Read the authenticated customer's cart |
| `POST` | `/cart/items` | Customer | Add a product and positive quantity |
| `PATCH` | `/cart/items/:productID` | Customer | Set a cart-line quantity |
| `DELETE` | `/cart/items/:productID` | Customer | Remove a cart line |
| `POST` | `/orders` | Customer | Checkout the current cart with a shipping address |
| `GET` | `/orders` | Customer | List only the authenticated customer's orders |
| `GET` | `/orders/:id` | Customer | Read only an order owned by the authenticated customer |
| `POST` | `/admin/categories` | Admin | Create a category |
| `PATCH` | `/admin/categories/:id` | Admin | Update/archive a category |
| `POST` | `/admin/products` | Admin | Create a product |
| `PATCH` | `/admin/products/:id` | Admin | Update/archive a product |
| `GET` | `/admin/orders` | Admin | List all orders with bounded pagination |
| `GET` | `/admin/orders/:id` | Admin | Read any order |
| `POST` | `/admin/orders/:id/cancel` | Admin | Cancel a pending order and restore stock once |
| `GET` | `/healthz` | Public | Liveness check |
| `GET` | `/readyz` | Public | Readiness check, including database connectivity |

### JSON contracts

Successful resource responses use `{"data": ...}`. Every collection endpoint (`GET /categories`, `GET /products`, `GET /orders`, and `GET /admin/orders`) returns `{"data":[...],"pagination":{"page":1,"page_size":20,"total":0}}`. `page` is one-based, `page_size` defaults to 20 and is capped at 100, and `total` is the total number of matching records before pagination. Error responses use the error envelope defined below.

- Registration and login accept `{"email":"...","password":"..."}`. Registration creates a customer and returns the public user fields (ID and email); login returns `{"data":{"access_token":"...","token_type":"Bearer","expires_at":"...","user":{"id":"...","email":"...","role":"..."}}}`.
- Product/category create requests require their documented writable fields. Product creation accepts `category_id`, `name`, `description`, `price_cents`, `stock`; updates accept only those fields and `active`, with omitted fields unchanged. Category creation accepts `name`; updates accept `name` and `active`, with omitted fields unchanged. IDs, role, prices, totals, and order state cannot be changed through customer routes.
- `POST /cart/items` accepts `{"product_id":"...","quantity":1}` and adds the submitted quantity to an existing line for that product. `PATCH /cart/items/:productID` accepts `{"quantity":1}` and sets the line to exactly that quantity. Both require quantity >= 1; zero is invalid and removal must use `DELETE`.
- `POST /orders` accepts `{"shipping_address":{"recipient_name":"...","line1":"...","line2":"...","city":"...","region":"...","postal_code":"...","country_code":"...","phone":"..."}}`. `recipient_name`, `line1`, `city`, and ISO 3166-1 alpha-2 `country_code` are required; the other address fields are optional. The returned order contains its ID, state, USD-cent totals, immutable line snapshots, shipping-address snapshot, and timestamps.
- Admin cancellation takes no request body. It returns the updated order on success.
- JWTs use HS256 and contain `sub` (user ID), `role`, `iat`, and `exp` claims. Tokens expire after the configured lifetime; no refresh-token flow is included.

Canonical resource shapes (timestamps are RFC 3339 strings; IDs are opaque strings):

```json
{"data":{"id":"category-id","name":"Books","active":true,"created_at":"2026-10-06T08:00:00Z","updated_at":"2026-10-06T08:00:00Z"}}
{"data":{"id":"product-id","category_id":"category-id","name":"Example","description":"Description","price_cents":1299,"stock":5,"active":true,"created_at":"2026-10-06T08:00:00Z","updated_at":"2026-10-06T08:00:00Z"}}
{"data":{"id":"cart-id","items":[{"product_id":"product-id","name":"Example","quantity":2,"unit_price_cents":1299,"line_total_cents":2598}],"total_cents":2598}}
{"data":{"id":"order-id","state":"pending","items":[{"product_id":"product-id","product_name":"Example","quantity":2,"unit_price_cents":1299,"line_total_cents":2598}],"shipping_address":{"recipient_name":"Customer","line1":"1 Main St","city":"Example City","country_code":"US"},"total_cents":2598,"created_at":"2026-10-06T08:00:00Z","updated_at":"2026-10-06T08:00:00Z"}}
```

The same category/product shape is used by their read and mutation responses; the order shape is used by customer/admin order detail and cancellation responses. Cart line prices and totals are server-calculated. Collection items use the corresponding resource shape, and their `pagination` object follows the semantics above.

Cart writes accept product identifiers and quantities only. Checkout derives current prices and totals from persisted catalog data, revalidates product state and stock, snapshots item names/prices and the submitted shipping address, and clears the cart only after the transaction succeeds. If any line is unavailable or any write fails, no stock, order, or cart change is committed.

Cancellation changes only a pending order. In one transaction it changes the state and restores stock for every order line. Repeated cancellation and cancellation of any other state return a conflict and do not alter inventory.

## Security, configuration, and errors

- Hash passwords with bcrypt; never return hashes or JWT signing material.
- Require `JWT_SECRET` at startup; it must contain at least 32 bytes and is used only with HS256. `JWT_TTL` configures token lifetime and defaults to `15m`.
- `ADMIN_EMAIL` and `ADMIN_PASSWORD` are optional but must be supplied together. If both are absent, no admin is provisioned. If both are supplied, startup creates that admin only when the email is absent; it never overwrites an existing account, and startup fails if that email belongs to a non-admin account.
- `PORT` defaults to `8080`; `DB_PATH` defaults to `./data/ecommerce.db`. Startup creates the database parent directory when needed and fails explicitly if configuration, directory creation, database opening, or migrations fail. Do not commit credentials or generated database files.
- Normalize and uniquely constrain emails. Validate request bodies, required address fields, IDs, positive quantities, pagination bounds, and allowed field updates.
- Enforce role checks for admin routes and ownership checks for every customer cart/order read or mutation.
- Use parameterized SQL and avoid logging passwords, tokens, or full authentication headers.
- Use a consistent JSON error envelope, for example `{"error":{"code":"...","message":"..."}}`. Use 400 for invalid input, 401 for missing/invalid authentication, 403 for insufficient role, 404 for absent resources, 409 for state/stock conflicts, and 500 for unexpected failures. Do not expose internal error details in 500 responses.
- Fail startup on configuration or migration errors; provide a readiness result that fails when the database cannot be used. `pending` and `cancelled` are the complete order states in this milestone; there is no persisted payment status.

## Verification

- Unit-test service rules, validation, authorization/ownership, and order state transitions.
- Use temporary SQLite databases to test migrations, repository behavior, constraints, and persistence.
- Exercise handlers with `httptest`, including successful and rejected requests.
- Test checkout transaction rollback for insufficient stock/failure, concurrent attempts for limited stock, and cancellation stock restoration exactly once.
- Test that password hashes and secrets never appear in public responses.
- Run Go formatting, `go test ./...`, and `go vet ./...` after implementation.

## Completion criteria

- The API starts with documented environment configuration and exposes health/readiness endpoints.
- Migrations create a usable SQLite schema from an empty database.
- Customer and admin authorization is enforced on all protected routes.
- A customer can register, browse active products, maintain a cart, place an order with a shipping address, and retrieve only their own orders.
- An admin can manage the catalog, inspect orders, and cancel a pending order without risking overselling or duplicate stock restoration.
- Automated tests verify persistence, authorization, checkout, inventory, cancellation, and error behavior.
